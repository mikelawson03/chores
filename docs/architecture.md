## Purpose
The application is a household management platform. The current MVP focuses on chore scheduling and assignment. Future modules may include calendars, shopping lists, allowance tracking, and household coordination tools.


## Architectural Layers
### API Layer (internal/api)

Responsibilities:
- HTTP routing
- Request decoding
- Request contract validation
- Response formatting
- Authentication middleware

Does not contain:
- Business logic
- Database logic

### App Layer (internal/app)

Responsibilities:
- Business rules
- Authorization
- Scheduling logic
- Balancing logic
- Domain validation

Examples:
- User may only edit their own assignment
- Scheduler generates missing assignments
- Balancer distributes workload

### Store Layer (internal/store)

Responsibilities:
- Persistence abstraction
- Data retrieval
- Data storage

Purpose:
Separates business logic from database implementation.

### Database Layer

Responsibilities:
- SQL queries
- Database-specific implementation

## Workflow Design Principle
Dependencies flow downward; data flows upward.

### Request Flow
```
HTTP Request            Client
↓                       ↑
API Layer               HTTP Response
↓                       ↑
App Layer               Business Result
↓                       ↑
Store Layer             Domain Object(s)
↓                       ↑
Database →   →   →   →  Database result
```

### Rationale
This keeps business logic independent from transport and persistence concerns.

For example:
- App logic should not know whether requests came from HTTP, WebSockets, CLI, or another source.
- Store layer should not care why a record is being stored or retrieved; it just knows what data lives where

## Core Domain Concepts

### User
Represents a household member.

### Chore Template
Defines a recurring chore.

Contains:
- Cadence
- Duration
- Ownership
- Optional Template Assignee

### Assignment
A scheduled instance of a chore template.

Generated by:
- Scheduler

Acts upon:
- Completion
- Cancellation
- Editing

### Scheduler
Ensures assignments exist within the planning horizon. Creates missing assignments.

Reference:
See `./docs/scheduler.md`

### Balancer
Distributes unassigned chores among users.

Reference:
See `./docs/balancer.md`

### Scheduler/Balancer Relationship
Scheduler does not invoke Balancer. Balancer does not invoke Scheduler.

Automated jobs may run both sequentially.

## Design Principles

- **Thin Handlers** - handlers should just decode requests and call the appropriate app logic
- **Business Logic Lives in App Layer** - Validation, authorization, scheduling, and balancing belong in the app layer.
- **Store Layer is Persistence Only** - Store functions should not enforce business rules.
- **Idempotent Scheduler** - running the scheduler repeatedly should not create duplicate assignments.
- **Again, Dependencies Flow Downward; Data Flows Upward** - the App layer should not know about HTTP requests, nor should it care how the data is stored. The Store should not know why data is being stored; it should just know where it goes.
